# CC98 新帖扫描与通知流程重构方案

> 状态：后端已实施，前端待实施
> 整理日期：2026-09-02
> 适用仓库：cc98-ai-improvement-backend 与 cc98_hackthon_frontend

## 1. 背景与目标

当前后端已经能够定时扫描 CC98 新帖、匹配用户订阅并通过邮箱或钉钉发送提醒，但现有实现把“帖子扫描”“匹配结果”“外部渠道投递”“前端消息历史”混在一套通知状态模型里，带来了以下问题：

- /topic/new 每轮只读取最新 20 帖，扫描游标只写不读；20 条以外的新帖可能漏掉。
- 当前游标保存的是本页最后一条帖子，而接口按从新到旧返回，因此游标语义错误。
- Notification 以 (user_id, subscription_id, topic_id) 去重；同一用户的多条订阅匹配同一帖子时会产生多行，再依赖发送前二次去重。
- failed 通知会在后续每轮扫描中无限重试，永久错误可能不断积压。
- 邮箱和钉钉采用“第一个成功即返回”的故障转移语义，不能同时提醒。
- 前端插件每 5 分钟后台轮询通知列表，用户没有主动查看时也会持续消耗服务器和浏览器资源。
- sent 只是退出活动队列，历史行并没有从数据库删除；接口返回最近 100 条也不等于数据库只保留 100 条。

本次重构采用以下产品定位：

1. **前端通知列表是用户匹配结果的可靠消息中心。**
2. **邮箱和钉钉只是可选的、尽力而为的附加提醒。**
3. **外部渠道每批最多尝试一次，失败不自动补发。**
4. **一个用户对一个帖子最多保存一条通知，不关心它由哪条订阅触发。**
5. **一个用户使用一个统一提醒频率，所有启用渠道在同一轮尝试发送。**

这套取舍优先保证实现简单、队列有界、外部提醒不重复；代价是外部渠道可能因超时或进程崩溃漏发，但匹配结果始终能通过前端通知列表查看。

## 2. 核心概念和职责边界

重构后只保留两个“进度”概念。

### 2.1 全站扫描游标

SystemCursor 记录上次已持久化处理的最新 CC98 帖子，用于确定下一轮需要扫描哪些新帖。

它解决的是：

> 哪些 CC98 帖子是上次扫描以后出现的？

### 2.2 简单外部提醒队列

Notification.dispatch_pending 表示一条匹配结果是否还在等待本轮外部渠道处理。

它解决的是：

> 这条匹配结果是否还需要在用户的提醒周期到达时，向当前启用渠道尝试发送一次？

不再引入：

- 每条通知的邮箱状态；
- 每条通知的钉钉状态；
- 每渠道通知游标；
- pending / sent / failed / partial 多状态投递机；
- 独立投递表；
- 失败后的跨扫描自动重试。

## 3. 目标数据结构

### 3.1 CC98Topic

继续以 topic_id 作为主键并执行 upsert：

- 第一次见到：插入；
- 再次见到：更新标题、作者、板块、抓取时间和原始数据；
- 不因分页重叠产生重复帖子行。

游标可以减少重复扫描，但不能替代数据库主键。分页移动、任务崩溃、游标更新失败都可能导致同一帖子再次进入处理流程，数据库约束必须继续承担最终兜底。

### 3.2 Notification

建议调整为：

~~~text
id
user_id
topic_id
topic_title
topic_url
matched_reason
dispatch_pending
dispatch_processed_at
created_at

UNIQUE(user_id, topic_id)
INDEX(user_id, id)
INDEX(user_id, dispatch_pending, id)
~~~

删除或停止使用：

~~~text
subscription_id
delivery_channel
delivery_status
sent_at
is_read
~~~

设计含义：

- 一个用户对一个帖子只保存一条匹配结果。
- Notification 首先是前端消息中心的一条历史记录，其次才可能短暂进入外部提醒队列。
- matched_reason 继续保存在通知表中，只保留第一条匹配订阅产生的原因。
- dispatch_pending 只表达“尚未完成一次外部提醒处理”，不表达最终是否送达。
- dispatch_processed_at 记录该通知何时退出外部提醒队列。

### 3.3 NotificationChannel

建议继续保留已有配置，并补充或明确以下运行状态：

~~~text
last_attempted_at
last_sent_at
last_dispatch_status
last_dispatch_error

UNIQUE(user_id, provider)
~~~

其中：

- last_attempted_at：最近一次实际尝试外部发送的时间；
- last_sent_at：最近一次外部发送成功的时间；
- last_dispatch_status：渠道最近一次正式投递结果，例如 sent 或 failed；
- last_dispatch_error：供管理端和前端展示的最近正式投递错误；
- (user_id, provider) 唯一约束确保每个用户最多一个邮箱渠道和一个钉钉渠道。

渠道失败只是渠道最近一次运行结果，不再把对应通知重新放回队列。

### 3.4 用户级提醒频率

提醒频率应从“渠道级”收敛为“用户级”：

~~~text
notify_interval_minutes
last_dispatch_started_at
~~~

推荐作为用户通知偏好字段保存。所有启用渠道在同一提醒周期内一起处理。

这样做的原因是：如果邮箱和钉钉允许不同频率，一个简单的共享队列无法判断某条通知是否已经分别被两个渠道处理，最终仍会重新引入每渠道游标、每渠道状态或独立投递表。统一频率是保持当前模型简单的必要产品约束。

有效提醒间隔仍应满足：

~~~text
effective_interval = max(SCAN_INTERVAL_MINUTES, user_notify_interval_minutes)
~~~

服务器当前扫描间隔为 10 分钟，因此当前最短有效提醒频率也是 10 分钟。

频率判断只读取用户级 `last_dispatch_started_at`。它在一轮用户投递开始、外部渠道调用之前更新一次；邮箱和钉钉各自的 `last_attempted_at` 仅用于渠道诊断，不能参与用户频率判断，否则串行发送耗时会把下一轮从 10 分钟误推迟到 20 分钟。判断时允许 `NOTIFICATION_DUE_GRACE_SECONDS`（默认 5 秒）的调度抖动。

## 4. 新帖接口与扫描游标

### 4.1 已验证的分页方式

CC98 新帖接口支持：

~~~http
GET /topic/new?from=0&size=20
GET /topic/new?from=20&size=20
GET /topic/new?from=40&size=20
~~~

size=20 表示本页数量，from 表示偏移量。无需尝试一次请求 40 条，应按 20 条逐页获取。

2026-09-02 在服务器上进行只读验证时得到：

~~~text
数据库旧游标：6608896

from=0   6608920 ... 6608901，共 20 条
from=20  6608900 ... 6608881，共 20 条，旧游标位于本页第 5 条
from=40  6608880 ... 6608861，共 20 条
from=60  6608860 ... 6608841，共 20 条
~~~

相邻页当时没有重叠，返回顺序为从新到旧。

### 4.2 新帖接口也需要限速

实际测试中，第一页请求成功后立即请求第二页，第二页返回空响应体的 HTTP 403；页间等待 2 秒后分页成功。这高度符合接口限流特征，但空响应体不足以证明具体限流规则。

实现时应：

- 为 /topic/new 单独增加最小请求间隔，建议先按 2 秒配置；
- 对 403 做有限次数重试和退避；
- 不要只复用当前仅作用于搜索接口的限速逻辑；
- 记录页码、偏移量、HTTP 状态和重试次数，但不要记录访问令牌。

### 4.3 正确的游标语义

接口按从新到旧返回，因此游标必须保存：

> 本轮第一页的第一条帖子 ID，即本轮扫描开始时看到的最新帖子。

当前实现循环覆盖 latest_topic_id，最后保存第一页最后一条，也就是本页最旧的帖子。旧游标因此不能被解释为真正的“上次最新帖”。

正确逻辑：

~~~python
first_page = get_new_posts(limit=20, offset=0)
new_cursor = first_page[0]["topic_id"] if first_page else None
~~~

只有当新帖、匹配结果和通知记录已经可靠提交后，才能把数据库游标更新为 new_cursor。

### 4.4 分页停止条件

推荐伪代码：

~~~python
old_cursor = load_cursor()
new_cursor = None
offset = 0
seen_topic_ids = set()
new_topics = []
cursor_boundary_reached = False

while True:
    page = get_new_posts(limit=20, offset=offset)

    if offset == 0 and page:
        new_cursor = page[0]["topic_id"]

    for topic in page:
        topic_id = int(topic["topic_id"])

        if topic_id <= int(old_cursor):
            cursor_boundary_reached = True
            continue

        if topic_id not in seen_topic_ids:
            seen_topic_ids.add(topic_id)
            new_topics.append(topic)

    if cursor_boundary_reached or len(page) < 20:
        break

    offset += 20
    wait_for_new_posts_rate_limit()
~~~

### 4.5 为什么仍要做页内 seen_topic_ids

from 是实时列表的偏移量，不是服务端快照游标。抓取第一页和第二页之间如果出现新帖、删帖或隐藏帖，第二页的位置可能移动：

- 同一帖子可能在相邻两页重复；
- 极端情况下也可能跳过边界帖子。

因此单轮分页仍要按 topic_id 做内存去重。还可以让相邻页保留少量重叠，例如每次偏移 15 而不是 20，以降低实时列表移动造成漏帖的概率；最终仍由 topic_id 去重。

### 4.6 游标缺失和最大页数

必须设置最大分页数量，避免游标丢失时无限抓取，例如：

~~~text
MAX_NEW_POST_PAGES = 10
~~~

旧游标对应的帖子可能在两轮扫描之间被删除、隐藏或改变状态，因此停止条件不能要求精确找到旧游标。只要出现任意 `topic_id <= old_cursor`，就说明扫描已经越过上轮边界；只有达到上限后抓到的帖子仍全部大于旧游标，才视为游标缺口。

如果达到上限仍未越过旧游标边界：

- 标记 worker 为 cursor_gap 或等价异常状态；
- 保留已抓到和已持久化的数据；
- 不应在没有告警的情况下直接推进游标并宣称扫描完整；
- 由运维人员决定扩大回溯页数，或接受缺口并重新建立基线。

### 4.7 首次运行与旧游标迁移

首次部署必须明确策略：

- **建立基线**：把当前最新帖子设为游标，不提醒历史帖子；
- **有限回填**：回溯指定页数并生成历史匹配结果。

本次从旧逻辑迁移时，旧游标通常是上次第一页的末尾。可以在新逻辑首次运行时继续读取它并向下分页：这会重复匹配上次已经处理过的约 19 条帖子，但新的 (user_id, topic_id) 唯一约束会阻止重复通知；同时可以避免直接重置游标造成漏帖。首次成功完成后，再把游标修正为本轮第一页第一条。

## 5. 匹配与通知创建流程

### 5.1 第一条匹配订阅胜出

订阅按 ID 升序读取：

~~~python
subscriptions = (
    db.query(Subscription)
    .filter(Subscription.status == "enabled")
    .order_by(Subscription.id.asc())
    .all()
)
~~~

对每个帖子维护：

~~~python
matched_user_topics: set[tuple[str, str]]
~~~

处理规则：

1. 按订阅 ID 顺序匹配；
2. 某用户的第一条订阅匹配该帖子后，创建一条 (user_id, topic_id) 通知；
3. 将组合加入 matched_user_topics；
4. 后续属于同一用户的订阅不再匹配该帖子；
5. matched_reason 直接使用第一条命中订阅产生的原因。

不选择最高置信度，也不汇总多个订阅原因。这一选择牺牲部分解释完整度，换取更简单、稳定且容易去重的行为。

### 5.2 数据库唯一约束仍是最终保障

内存集合只能处理当前进程、当前扫描内的重复，数据库必须增加：

~~~text
UNIQUE(user_id, topic_id)
~~~

它用于防止：

- 同一帖子下一轮再次进入扫描；
- 分页重叠；
- 游标未及时更新；
- 任务崩溃后重跑；
- 并发扫描；
- 用户删除并重新创建相似订阅后重复收到旧帖子。

### 5.3 指标语义应同步调整

当前 fetched_topics 统计的是参与 upsert 的输入数量，不是数据库新插入帖子数；matched_pairs 也可能包含最终被唯一约束拦截的重复匹配。重构后建议使用更明确的指标：

~~~text
fetched_pages
fetched_topic_items
unique_topics_before_cursor
scanned_subscriptions
candidate_pairs
matched_user_topics
created_notifications
queued_notifications
dispatch_batches
dispatch_attempts
dispatch_successes
dispatch_failures
deduplicated_destination_topics
~~~

指标名称要区分“API 返回数量”“唯一新帖数量”“匹配成功数量”“真正创建的通知数量”和“外部请求数量”。

## 6. 简单队列与提醒周期

### 6.1 入队规则

匹配成功创建 Notification 时：

- 用户至少启用了一个外部渠道：dispatch_pending = true；
- 用户没有启用任何外部渠道：dispatch_pending = false。

两种情况都会保存通知并允许前端查询。没有外部渠道时不应让通知永久停留在提醒队列中。

用户以后启用邮箱或钉钉时，默认只提醒启用以后产生的新通知，不回填旧历史。

### 6.2 健康队列的周转周期

到达用户提醒时间后，查询：

~~~sql
SELECT *
FROM notifications
WHERE user_id = ?
  AND dispatch_pending = true
ORDER BY id ASC;
~~~

正常情况下，一条待处理通知最多等待约一个用户提醒周期，再加少量定时任务抖动。因此最低提醒频率决定的是健康队列的最长常规停留时间，而不是历史数据在数据库中的保留时间。

到期判断使用用户级投递轮次开始时间：

~~~text
now + due_grace >= last_dispatch_started_at + notify_interval
~~~

开始处理一个用户时只更新一次 `last_dispatch_started_at`，之后邮件、钉钉以及多个批次各自更新渠道时间，但不会改变本轮的用户级频率起点。

### 6.3 先出队，再发送

本项目接受外部渠道失败不补发，因此采用“至多尝试一次”的处理顺序：

1. 读取本轮 dispatch_pending = true 的通知；
2. 形成当前轮次的发送计划；
3. 将这些通知设为 dispatch_pending = false，写入 dispatch_processed_at 并提交；
4. 尝试发送邮箱；
5. 尝试发送钉钉；
6. 分别更新渠道级 last_attempted_at / last_sent_at / last_dispatch_status / last_dispatch_error；
7. 无论发送成功、失败或进程后续异常，都不重新入队。

先出队的理由：

- 外部平台可能已经收到消息，但服务器读取响应时超时；如果保留在队列，下次会重复发送；
- 进程在邮箱成功、钉钉尚未处理时崩溃，重新执行也可能重复发送邮箱；
- 前端通知中心已经保存匹配结果，因此外部提醒可以优先选择“不重复”而不是“保证到达”。

这属于 **at-most-once（至多一次）** 语义：可能漏发，但正常情况下不会因为自动重试而重复发送。

### 6.4 不保留活动 failed 队列

不再把失败通知加入下一轮查询，也不做跨扫描自动重试。

需要保留的是渠道最近一次结果，而不是每条通知的失败状态：

~~~text
NotificationChannel.last_dispatch_status = failed
NotificationChannel.last_dispatch_error = 用户可理解的错误摘要
~~~

前端可以提示：

~~~text
最近一次钉钉提醒发送失败，请检查 Webhook。
相关帖子仍可在通知列表中查看，本批次不会自动补发。
~~~

用户修复配置后，“测试渠道”只发送测试消息，不自动补发历史通知。

## 7. 邮箱、钉钉与同一目的地去重

### 7.1 所有启用渠道都尝试一次

删除当前“第一个渠道成功就 return”的逻辑。每个用户到达提醒时间时，对当前所有启用渠道各尝试一次：

~~~text
邮箱成功、钉钉成功：两边都收到
邮箱成功、钉钉失败：不补钉钉，前端展示钉钉渠道错误
邮箱失败、钉钉成功：不补邮箱，前端展示邮箱渠道错误
两个都失败：前端通知列表仍可查看全部帖子
没有渠道：不发送，通知只存在于前端消息中心
~~~

### 7.2 单轮同一目的地去重

单轮调度内维护：

~~~text
(provider, normalized_destination) -> 已成功发送的 topic_id 集合
~~~

目的地规范化建议：

- 邮箱：去除首尾空格并转为小写；
- 钉钉：使用规范化 Webhook 的哈希作为内存键，避免在日志和指标中暴露 access token 或 secret；
- provider 必须是键的一部分，因此邮箱与钉钉不会互相去重。

规则：

1. 构建发送内容前，过滤该目的地本轮已成功发送的帖子；
2. 外部请求成功后，才把帖子加入已发送集合；
3. 如果请求失败，不加入集合，允许本轮另一个使用相同目的地的账户继续尝试；
4. 如果全部帖子都已由同一目的地成功处理，则不再调用外部平台；
5. 对被目的地去重覆盖的通知仍视为本轮已处理，不重新入队。

示例：

~~~text
用户 A，共享邮箱：帖子 1、帖子 2
用户 B，共享邮箱：帖子 2、帖子 3

最终该邮箱收到：帖子 1、帖子 2、帖子 3
~~~

### 7.3 分批连续发送

如果待提醒帖子过多，应按固定上限切分，例如每批最多 20 帖：

~~~text
第 1 批：1～20
第 2 批：21～40
第 3 批：41～60
~~~

这既避免邮件正文或钉钉消息过长，也允许同一目的地在一轮中连续收到多批通知。由于通知在外部发送前已经出队，后续某批失败也不会让前面的批次重新发送。

## 8. 前端通知列表刷新策略

### 8.1 删除后台五分钟轮询

删除 service worker 中的 badge-poll 周期任务，并在插件升级或启动时显式执行：

~~~javascript
chrome.alarms.clear("badge-poll")
~~~

只删除 alarm 的创建代码不够，已经存在的 alarm 可能继续运行。当前插件采用手动加载方式，旧版本用户还需要重新加载插件才能获得新逻辑。

取消轮询后的产品变化：

- 用户不打开通知列表时，不再向服务器请求；
- 没有配置邮箱或钉钉的用户，只能在主动打开列表后发现新通知；
- 不再保证后台实时未读徽章；
- 徽章使用前端本机保存的 lastSeenNotificationId，只在用户主动打开插件或刷新列表后更新；后端不保存 is_read。

### 8.2 主动查看和手动刷新

推荐前端规则：

~~~text
用户打开通知面板
    ├─ 距离上次成功刷新不足 60 秒：显示本地缓存
    └─ 已达到 60 秒：请求后端并更新缓存

用户点击手动刷新
    ├─ 不足 60 秒：显示剩余冷却时间
    └─ 已达到 60 秒：请求后端
~~~

应分别记录：

- lastAttemptAt：避免网络失败后按钮被连续点击；
- lastSuccessAt：向用户展示“最后更新于……”；
- 最近一次成功响应的通知缓存。

手动刷新只读取后端已经生成的通知，绝不能触发 /api/v1/tasks/scan 或直接调用 CC98 新帖接口。

认证失败时应清除无效令牌、停止后台动作并引导重新登录，不能继续每隔固定时间产生 401。

## 9. 后端通知接口限频和入口防护

### 9.1 用户级 60 秒限频

GET /api/v1/notifications 应限制为：

> 同一已认证用户每 60 秒最多成功读取一次。

超限返回：

~~~http
HTTP/1.1 429 Too Many Requests
Retry-After: 42
~~~

限频范围应只针对通知列表接口，不应把用户的其他正常操作一并锁住。

### 9.2 60 秒用户限频不等于防 DDoS

用户级限频只能减少：

- 插件异常轮询；
- 用户连续点击；
- 单个有效令牌的滥用。

它不能阻止大量 IP、大量令牌或未认证请求打到应用。真正的入口防护应在应用之前完成：

- 让 Uvicorn 只监听 127.0.0.1:8000；
- 使用 Nginx、Caddy 或可信 CDN 暴露公网入口；
- 在认证和数据库查询之前按来源 IP 做基础限频；
- 只信任来自已知反向代理的 X-Forwarded-For；
- 对验证码、登录、通知列表等接口分别设置合适的限制；
- 对异常状态码和请求量做监控。

即使暂时仍直接暴露后端端口，也应认识到应用内的每用户限频不是完整的 DDoS 方案。

## 10. 通知列表、历史数据与保留策略

### 10.1 所有用户共用数据库

当前所有用户共用一个 SQLite 数据库，通过 Notification.user_id 区分数据，不是每个用户一个数据库。

通知列表接口必须保持以下查询顺序：

~~~sql
WHERE user_id = 当前认证用户
ORDER BY id DESC
LIMIT 100
~~~

含义是先筛选当前用户，再返回该用户最近 100 条；不是先取全站 100 条再过滤。请求参数中的 user_id 不应作为权限依据，身份必须来自认证令牌。

### 10.2 LIMIT 100 不是数据清理

接口只返回最近 100 条，并不会删除第 101 条及更早的数据。重构后的 dispatch_pending = false 也只是退出外部提醒队列，历史行仍然保存在数据库里。

因此需要把两个问题分开：

- **队列周转**：由用户提醒频率和一次性出队逻辑决定；
- **历史保留**：由独立的数据保留策略决定。

历史保留策略尚未最终确认，可以后续选择：

- 每用户保留最近固定数量，例如 1000 条；
- 保留固定时间，例如 90 天；
- 两者同时使用，先满足任一上限即清理。

历史清理应由低频维护任务完成，不应混入每轮新帖扫描的主路径。

## 11. 目标端到端流程

~~~text
定时扫描开始
    ↓
加载正确的最新帖高水位游标
    ↓
调用 /topic/new?from=0&size=20
    ↓
按 20 条分页并限速，直到遇见旧游标
    ↓
单轮按 topic_id 去除分页重叠
    ↓
CC98Topic 按 topic_id upsert
    ↓
订阅按 id 升序参与匹配
    ↓
同一 user_id + topic_id 第一条匹配胜出
    ↓
Notification 由 UNIQUE(user_id, topic_id) 最终去重
    ↓
无外部渠道：直接作为前端历史，不入提醒队列
有外部渠道：dispatch_pending = true
    ↓
持久化成功后更新扫描游标为第一页第一条
    ↓
到达用户统一提醒时间
    ↓
构建本轮按目的地去重、按大小分批的发送计划
    ↓
先把本批通知设置为 dispatch_pending = false 并提交
    ↓
邮箱和钉钉各尝试一次，不因其中一个成功而提前返回
    ↓
只在 NotificationChannel 记录最近成功或失败
    ↓
失败不重新入队，用户始终可在前端通知列表查看帖子
~~~

## 12. 迁移建议

实施前应先备份数据库并验证备份哈希。SQLite 没有现成 Alembic 迁移体系时，修改唯一约束通常需要重建表，不能只增加一条 ALTER TABLE。

建议迁移顺序：

1. 停止扫描任务，避免迁移期间产生新通知；
2. 备份数据库；
3. 建立新的通知表结构；
4. 按 (user_id, topic_id) 对旧通知去重；
5. 每组保留 ID 最小或创建时间最早的一条，并保留其 matched_reason；
6. 所有旧通知迁移为 dispatch_pending = false，避免部署后突然补发历史记录；
7. 建立 (user_id, topic_id) 唯一约束及队列、列表复合索引；
8. 为渠道建立 (user_id, provider) 唯一约束，并在迁移前处理潜在重复渠道；
9. 将提醒频率迁移到用户级设置；
10. 部署支持分页和正确游标语义的新扫描逻辑；
11. 新逻辑首次使用旧尾部游标做一次安全回放，依赖新唯一约束消除重复；
12. 成功后将游标更新为本轮第一页第一条；
13. 更新前端并显式清除旧 badge-poll alarm；
14. 先手动扫描验证，再恢复定时任务。

迁移去重时要明确：旧表中同一用户、同一帖子可能有多条不同订阅记录。按照新规则只保留第一条，不汇总匹配原因，也不保留订阅来源。

## 13. 测试清单

### 13.1 扫描游标

- 游标位于第一页中部：只处理编号大于游标的新帖；
- 游标帖子被删除或隐藏：遇到首条编号小于游标的帖子后正常结束；
- 第一页 20 条全部在游标之后：继续读取 from=20；
- 游标位于第三页或更深：连续分页直到越过其编号；
- 相邻页重复 topic：只处理一次；
- /topic/new 请求过快返回 403：按退避规则重试；
- 页面不足 20 条：正确停止；
- 空页面：安全结束；
- 达到最大页数仍未出现编号小于等于游标的帖子：报告 cursor_gap；
- 通知持久化失败：不推进游标；
- 持久化成功但更新游标前崩溃：重跑后由唯一约束去重；
- 新游标始终是第一页第一条，不是最后一条。

### 13.2 匹配与通知唯一性

- 同一用户一条订阅匹配：产生一条通知；
- 同一用户多条订阅匹配：只保留订阅 ID 最小的第一条原因；
- 不同用户匹配同一帖子：每个用户各一条通知；
- 下一轮重复扫描同一帖子：不产生新通知；
- 删除并重建订阅：旧帖子不重新产生通知；
- 并发尝试插入同一 (user_id, topic_id)：数据库唯一约束生效。

### 13.3 简单提醒队列

- 用户没有渠道：通知可在前端查询，但不进入队列；
- 只有邮箱：到提醒时间只尝试邮箱一次；
- 只有钉钉：到提醒时间只尝试钉钉一次；
- 两个渠道：两边各尝试一次；
- 一个成功、一个失败：不重试，渠道状态分别更新；
- 两个都失败：通知已出队，前端仍能查询；
- 在外部调用前进程崩溃：通知不重新入队；
- 同一目的地多个账户有相同帖子：单轮只发送一次；
- 第一位账户发送失败：第二位相同目的地账户仍可尝试；
- 超过单批上限：拆成多批连续发送。

### 13.4 前端和接口限频

- 安装或升级后旧 badge-poll 被清除；
- 插件空闲时不再请求通知接口；
- 打开通知列表且缓存超过 60 秒：请求一次；
- 60 秒内再次打开：使用缓存；
- 60 秒内点击手动刷新：显示冷却时间；
- 后端同一用户 60 秒内重复请求：返回 429 和正确 Retry-After；
- 不同用户互不影响；
- 401 后清理令牌并停止后台请求；
- 手动刷新不会触发全站扫描；
- 查询结果只包含当前认证用户最新 100 条。

## 14. 关键 know-how 总结

### 14.1 游标用于缩小工作集，唯一约束负责正确性

不要把扫描游标当作唯一去重保障。游标会因崩溃、分页移动或迁移错误而失效；数据库唯一约束才是最终正确性边界。

### 14.2 新帖高水位应指向列表头部

对于从新到旧的列表，新的高水位是第一页第一条。保存第一页最后一条会人为制造一个约 19 条的重叠窗口，并让游标无法代表上次最新帖。

### 14.3 偏移分页不是快照

from=20 表示当前时刻列表中的第 21 条，不保证与请求第一页时属于同一快照。必须允许页间重复，并使用 topic ID 去重；必要时可以主动设置页间重叠。

### 14.4 第一条匹配必须有稳定顺序

既然产品选择“第一条订阅命中即停止”，就要显式按订阅 ID 排序。没有 ORDER BY 的数据库结果顺序不应被当作业务语义。

### 14.5 出队不等于删除历史

dispatch_pending = false 只表示不再参加外部提醒处理。通知行仍是前端消息历史。接口 LIMIT 100 也只是展示窗口，不是保留策略。

### 14.6 先出队再发送意味着 at-most-once

先提交出队状态再调用外部平台，可以避免超时和崩溃后的自动重复，但允许漏发。这个取舍只有在前端消息中心是可靠兜底时才成立。

### 14.7 不补发仍然需要记录渠道错误

不建立失败队列，不代表忽略错误。服务器仍要保存渠道最近一次错误，前端负责把可操作信息反馈给用户，管理员日志保留更详细的技术原因。

### 14.8 单一用户频率换来单一共享队列

如果两个渠道需要不同频率，就必须分别记录处理进度。统一为用户级频率，才能安全地让一批通知在一个周期内同时交给所有渠道并一次出队。

### 14.9 同一目的地去重只在成功后生效

如果发送失败就把帖子加入“已发送集合”，会阻止本轮其他账户使用同一目的地继续尝试。只有外部请求成功后，才能登记为本轮已发送。

### 14.10 用户级限频不是 DDoS 防护

每用户 60 秒一次可以控制正常客户端和单令牌滥用，但请求仍然已经到达服务器。入口级 IP 限频、反向代理、端口隔离和流量清洗承担的是不同层次的安全职责。

## 15. 未来何时需要重新引入投递表

当前简单模型适用于：

- 只有邮箱和钉钉两个固定渠道；
- 所有渠道共享用户提醒频率；
- 外部发送失败不补发；
- 不要求查询每条通知在每个渠道上的投递历史；
- 前端通知列表是最终兜底。

如果未来出现以下需求，应重新评估独立投递表：

- 邮箱和钉钉使用不同频率；
- 失败必须自动重试；
- 必须分别展示每条通知的渠道状态；
- 一个用户允许配置多个同类型目的地；
- 需要严格审计投递历史；
- 增加飞书、短信、微信等动态渠道；
- 要求至少一次投递或更强可靠性。

届时独立的 (notification_id, channel_id) 投递记录不再是“过度设计”，而是表达这些产品需求所必需的数据模型。
